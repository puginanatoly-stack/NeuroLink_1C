# /release-analysis — анализ времени выпуска релизов 1С-конфигурации

Методика одобрена пользователем 25.08.2026 («ты молодец») — переиспользовать для любых будущих релизов.
Полная история и выводы — `TOOLI-MEMORY.md §19`.

## Объекты и источники данных

- **Проект:** GitLab `<namespace>/<project>` (id **`<id>`**, пример ниже использует placeholder `7266`), регламент — `GIT_WORKFLOW.md`. CI-конфиги — отдельный репо с общими pipeline-шаблонами (пример id `7426`), путь `<namespace>/<project>/`.
- **GitLab API:** `glab` (`$env:LOCALAPPDATA\Programs\GLab\glab.exe`), host `gitlab.example.com` (подставьте свой инстанс).
- **Jira API:** ваш проект (пример кода задач — `HR-xxxxx`), токен — User-env `JIRA_TOKEN`, базовый URL `https://jira.example.com`.
- **Второй агент:** отдельный Claude Code инстанс на другой машине. Обмен — файлами на общей сетевой шаре или git-репо.

## Модель процесса релиза (как реально)

1. Задачи (HR-*) → ветки `feature/fix/HR-*` → MR в **develop**.
2. Релизная ветка **release/X** (MR `develop → release/*`, иногда feature → release).
3. На ветке вручную гоняют **BDD (5 потоков) + Smoke (7 потоков)**, прогон 2.5–4 ч.
4. Ошибка → корректирующий коммит → новый MR в релизную ветку → прогон заново (цикл до зелёного).
5. Зелёный → **ручные тесты аналитиками** (1–3 суток, «чёрный ящик») → **тег релиза** → **деплой артефактов** (минуты).

## Сбор данных (по шагам)

### 1. Пайплайн/релизные MR
```powershell
$glab = "$env:LOCALAPPDATA\Programs\GLab\glab.exe"
# MR по майлстоуну (задачи + релизные MR)
& $glab api --hostname "gitlab.example.com" "projects/7266/merge_requests?milestone=3.1.37.49011&state=all&per_page=100"
# Тестовые прогоны релизного MR — ВАЖНО: ref с префиксом refs/merge-requests/<iid>/head
& $glab api --hostname "gitlab.example.com" "projects/7266/pipelines?ref=refs/merge-requests/2134/head&per_page=100"
```

### 2. Тестовый прогон = пайплайн с реально выполненными BDD/Smoke
- Фильтр: у пайплайна есть джобы `*BDD*`/`*Smoke*` со статусом ≠ `manual`, длительность пайплайна **>500с**.
- «Мгновенные» провалы (1–312с, BDD/Smoke не стартовали) — **шум** (Vault script_failure / ручная отмена дубля), из тест-времени исключать.
- Джобы: `projects/7266/pipelines/<pid>/jobs?per_page=100`.

### 3. Причины падений BDD — из trace джобы
`projects/7266/jobs/<job_id>/trace` (последние строки):
- `execution took longer than 3h0m0s` — **таймаут 3ч** (завис внешний обмен/синхронизация) — самая дорогая причина.
- `TestClient ... Не получилось подключить / Ошибка сетевого взаимодействия` — инфраструктура, тесты не стартовали.
- `Таблица <X>. Ожидали A, получили B` / `В табличном документе N строк, ожидалось M` / `Окно ... не найдено, таймаут` — хрупкие ожидания сценария.

### 4. Очередь vs реальное время
`projects/7266/pipelines/<pid>` → поле **`queued_duration`**. В наблюдаемых прогонах: 1–16с у всех — очереди НЕТ, разброс длительности = реальное время выполнения (не трогать раннеры).

### 5. Jira
- Типы задач по релизу: `GET /rest/api/2/search?jql=fixVersion = "X"&maxResults=200&fields=key,issuetype,status,created` (URI кодировать `[uri]::EscapeDataString`).
- Workflow: `GET /rest/api/2/issue/<KEY>?expand=changelog` → `changelog.histories` (переходы статусов). ВАЖНО: статус «Тестирование» в workflow HR = приёмка разработчиком ДО релиза; статуса «ручное тестирование релиза аналитиками» НЕТ — окно «зелёный→тег» через Jira неразбиваемо.

### 6. Вливки в релизную ветку
Merged MR с `target_branch -like 'release/*'`, счёт: всего / develop→release / feature→release. Корреляция «вливки → прогоны»: порционная вливка = 3–5 прогонов, разовая сборка = 2.

## Генераторы отчётов (в `C:\Personal AI\scripts\`)

| Скрипт | Что делает | Файл-результат |
|---|---|---|
| `build-release-analysis.ps1` | Глубокий анализ N релизов (таблица, тренды, корреляции, идеи) | `docs\release-analysis-<диапазон>.html` |
| `build-release-comparison.ps1` | Сводка 4 релизов (модель процесса, прогоны, задачи) | `docs\release-comparison-*.html` |
| `build-release-confluence.ps1` | Автономный HTML-блок для макроса Confluence | `docs\release-analysis-confluence.html` |
| `build-release-timeline.ps1` | Временная шкала одного релиза | `docs\release-<версия>-timeline.html` |

**Обязательно после Write:** перекодировать `.ps1` в UTF-8 с BOM (PS 5.1 читает UTF-8 без BOM как ANSI → ломается кириллица/em-dash):
```powershell
$c = [System.IO.File]::ReadAllText($p, [System.Text.Encoding]::UTF8)
[System.IO.File]::WriteAllText($p, $c, (New-Object System.Text.UTF8Encoding($true)))
```

## Confluence-блок (проверенный формат)

- **Только автономный HTML** для HTML-макроса: `<div id='rlr'>` + `<style>` (все селекторы с префиксом `rlr`) + разметка, **без** `DOCTYPE/html/head/body`, без CDN/внешних скриптов (Confluence блокирует).
- Стиль: тёмная шапка-градиент, KPI-карточки, таблица с цветными чипами статусов (`.rlr-ok/.rlr-bad/.rlr-warn`), блоки-выводы (`.rlr-red/.rlr-green/.rlr-blue`), `.rlr-note` для пояснений.
- Проверить в браузере локально (Ctrl+P → А4), потом вставить содержимое в HTML-макрос.

## Взаимодействие со вторым агентом

- Фактура лежит на общей сетевой шаре или в общем git-репо (папка вида `release-timeline-<диапазон>/`).
- Он оставляет `REQUEST-*.md` / `ANSWER-*.md` — читать при появлении новых файлов.
- Ответ — файлом туда же, формат: от кого/кому/по поводу, данные по приоритетам, сырые JSON рядом, честно помечать «недоступно для анализа» если данных нет.

## Проверенные выводы (10 релизов, не пересобирать заново)

- Очередь раннеров = 1–16с — НЕ узкое место.
- Smoke ни разу не падал (0/32) — раздельный ретрай BDD/Smoke безопасен.
- Половина падений BDD — инфраструктурные (таймаут 3ч зависшего внешнего обмена, TestClient, сеть), не сценарии.
- Число прогонов зависит от способа вливки (порционная = 3–5, разовая = 2), не от объёма задач.
- Один из релизов — исторический выброс (34 вливки в release, включая 10 feature→release).
- Один из релизов не выпущен (MR closed, тега нет — объединён со следующим).
- Jira: типичный workflow `To Do → Анализ ЧТЗ → К разработке → Разработка → К приемке → Тестирование → В релиз → Done`; ручного тестирования релиза в нём нет.
